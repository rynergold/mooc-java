## 1. Inverting Conditions in Code

An `if` statement often starts with a positive check: it tests that every requirement passes.

```java
int score = 75;

// Positive check: valid only if both requirements pass
if (score >= 0 && score <= 100) {
    System.out.println("Valid score.");
}
```

### The Guard Clause Pattern: Rejection Checks

Programs often handle invalid input first and exit immediately. This pattern is called a **guard clause**.

To write a rejection check, identify what causes the input to fail:
- Valid: score is at least 0 and at most 100.
- Invalid: score is less than 0 or greater than 100.

Success requires every condition to pass (`&&`). Failure happens if any single condition goes wrong (`||`).

```java
// Rejection check (guard clause): exit early if anything is wrong
if (score < 0 || score > 100) {
    System.out.println("Invalid score.");
    return;
}

// If execution reaches here, the score is valid
System.out.println("Valid score: " + score);
```

### De Morgan's Laws: The Rule for Inverting Code

De Morgan's Laws define the rules for negating compound conditions.

To negate a compound condition, apply two steps:
1. **Flip every comparison operator to its opposite:**
   - `>=` flips to `<`
   - `<=` flips to `>`
   - `>` flips to `<=`
   - `<` flips to `>=`
   - `==` flips to `!=`
   - `!=` flips to `==`
2. **Swap the logical operator:**
   - `&&` becomes `||`
   - `||` becomes `&&`

### Example 1: Validating an Exam Score

Suppose a program accepts an exam score between `0` and `100` inclusive. Here are the two ways to write it:

```java
// Approach A: Positive check
if (score >= 0 && score <= 100) {
    System.out.println("Valid score");
} else {
    System.out.println("Invalid score");
}

// Approach B: Guard clause (De Morgan's Law)
if (score < 0 || score > 100) {
    System.out.println("Invalid score");
    return;
}
System.out.println("Valid score");
```

Here is how both approaches evaluate for different inputs:

| Test Input | Expected Result | Approach A: `score >= 0 && score <= 100` | Approach B: `score < 0 \|\| score > 100` | What Gets Printed |
| :--- | :--- | :--- | :--- | :--- |
| `score = 75` | Valid | `true` | `false` | Both print `"Valid score"` |
| `score = 150` | Invalid (too high) | `false` | `true` | Both print `"Invalid score"` |
| `score = -10` | Invalid (negative) | `false` | `true` | Both print `"Invalid score"` |

### Why the Boolean Values Are Opposites

Notice that for a valid input like `75`, Approach A evaluates to `true` while Approach B evaluates to `false`:
- **Approach A tests for success:** *"Is this score valid?"* For `75`, the answer is **YES (`true`)**.
- **Approach B tests for failure:** *"Is this score broken?"* For `75`, the answer is **NO (`false`)**.

Because the two conditions ask opposing questions, their boolean results are opposite. Both produce the exact same outcome: `75` is accepted.

### How De Morgan's Law Short-Circuits Early

The `||` operator in a guard clause gives you an automatic performance and safety benefit: **short-circuit evaluation**.

```java
if (score < 0 || score > 100)
```

- When `score = -10`: Java evaluates `-10 < 0`, which is `true`. Because `true || anything` is always `true`, Java **stops immediately** and runs the guard. It never evaluates the right-hand side (`-10 > 100`).
- The program exits at the first sign of trouble without doing unnecessary work.

### Example 2 (Medium): Bank Withdrawal

Moving from one variable to two variables: suppose an account has a `balance` and a user wants to withdraw an `amount`. A withdrawal is valid only if the amount is strictly positive AND does not exceed the balance.

```java
// Approach A: Positive check
if (amount > 0 && amount <= balance) {
    balance -= amount;
    System.out.println("Withdrawal approved: " + balance);
} else {
    System.out.println("Invalid withdrawal");
}

// Approach B: Guard clause (De Morgan's Law)
// Flip > to <=, flip <= to >, swap && to ||
if (amount <= 0 || amount > balance) {
    System.out.println("Invalid withdrawal");
    return;
}

balance -= amount;
System.out.println("Withdrawal approved: " + balance);
```

**Short-circuit in action:**  
If a user enters `-50`, the check `amount <= 0` is `true`. Java exits immediately. It never reads or evaluates `amount > balance`.

### Example 3 (Harder): Triangle Inequality

Moving from two conditions to three conditions: three sides `a`, `b`, `c` can form a triangle only if the sum of any two sides is strictly greater than the third side.

All three must pass:
```java
// Approach A: Positive check
if (a + b > c && b + c > a && c + a > b) {
    System.out.println("Valid triangle");
    return;
}
System.out.println("Invalid triangle");
```

Applying De Morgan's Law: flip every `>` to `<=`, and swap every `&&` to `||`:
```java
// Approach B: Guard clause (De Morgan's Law)
if (a + b <= c || b + c <= a || c + a <= b) {
    System.out.println("Invalid triangle");
    return;
}
System.out.println("Valid triangle");
```

**Short-circuit in action:**  
For sides `10, 3, 4`, the first test `b + c <= a` ($3 + 4 \le 10$) is `true`. Java short-circuits instantly on the first comparison and prints `"Invalid triangle"`. It skips the other two addition checks completely.

### The Common Inversion Mistake

When writing a guard clause, developers sometimes flip the comparisons but forget to swap `&&` to `||`:

```java
// WRONG: A number cannot be less than 0 AND greater than 100 at the same time
if (score < 0 && score > 100) { ... } // Never runs
```

### Formal Logic Notation

Formal logic represents these operations with symbols:

- Negation (`!` in Java): $\neg$
- AND (`&&` in Java): $\land$
- OR (`||` in Java): $\lor$
- Equivalence ("always identical"): $\iff$

De Morgan's Laws:

$$\neg (A \land B) \iff \neg A \lor \neg B$$
$$\neg (A \lor B) \iff \neg A \land \neg B$$

### Example 2 (Medium): Linear Tiered Ranges & Top-Down Exclusion

Categorizing a continuous variable into temperature bands:

- Below `0`: Freezing
- `0` to `20`: Cool
- `21` to `30`: Warm
- Above `30`: Hot

```java
int temp = 15;

if (temp < 0) {
    System.out.println("Freezing");
} else if (temp <= 20) {
    System.out.println("Cool");
} else if (temp <= 30) {
    System.out.println("Warm");
} else {
    System.out.println("Hot");
}
```

#### Top-Down Range Exclusion
Java evaluates `if` and `else if` statements in top-down order. Reaching `else if (temp <= 20)` guarantees that `temp < 0` evaluated to `false`. Therefore, `temp` is at least `0`. Writing `temp >= 0 && temp <= 20` is redundant.

#### Boundary Inclusivity
Check whether boundary thresholds are inclusive or exclusive:
- `< 20` excludes `20`.
- `<= 20` includes `20`.

### Example 3 (Harder): Hierarchical Branching & Multi-Attribute Matrices

Some classifications require hierarchical evaluation: validate prerequisites first, then determine sub-categories.

For example, classifying a triangle by its side lengths:
1. First verify the triangle inequality theorem ($a+b>c \land b+c>a \land c+a>b$). If violated, it is not a triangle.
2. If all three sides are equal: **Equilateral**.
3. If any two sides are equal: **Isosceles**.
4. Otherwise: **Scalene**.

```java
if (a + b <= c || b + c <= a || c + a <= b) {
    System.out.println("Invalid triangle");
} else if (a == b && b == c) {
    System.out.println("Equilateral");
} else if (a == b || b == c || a == c) {
    System.out.println("Isosceles");
} else {
    System.out.println("Scalene");
}
```

### Common Multi-Branch Pitfalls

- **Out-of-Order Conditions:** Ordering conditions from general to specific causes broader branches to swallow inputs before specific branches can run:
  ```java

      System.out.println("Pass");
  } else if (score >= 90) {
      System.out.println("Excellent");
  }
  ```
- **Redundant Range Checks:** Writing `else if (x >= 0 && x <= 20)` when the previous branch was `if (x < 0)`.

## 3. The Waterfall Pattern: Stepped Rates and Slices

Progressive taxes, utility rates, and stepped fees apply in tiers rather than a flat percentage across an entire total.

### Example 1: Free Allowance + Over-Quota Penalty

Suppose an airline baggage policy allows up to `20` kg free of charge. Any excess weight above `20` kg costs `10` euros per kilogram.

```java
int weight = 26;
int fee = 0;

if (weight <= 20) {
    fee = 0;
} else {
    // Only the excess (26 - 20 = 6 kg) is charged
    fee = (weight - 20) * 10;
}

System.out.println("Baggage fee: " + fee + " euros");
```

### Example 2 (Medium): Two-Tier Stepped Slice Calculation

A water utility charges:
- First 50 cubic meters: 1.00 euro per cubic meter.
- Volume above 50 cubic meters: 2.00 euros per cubic meter.

For 70 cubic meters:
1. The first 50 units fill Tier 1: $50 \times 1.00 = 50.0$ euros.
2. The remaining 20 units ($70 - 50$) spill into Tier 2: $20 \times 2.00 = 40.0$ euros.
3. Total cost = $50.0 + 40.0 = 90.0$ euros.

```
Total Usage: 70 units
[  0 to 50  ] -> 50 units * 1.00 = 50.0
[ 51 to 70  ] -> 20 units * 2.00 = 40.0
Total       = 90.0 euros
```

```java
int usage = 70;
double total = 0.0;

if (usage <= 50) {
    total = usage * 1.0;
} else {
    total = 50.0 + (usage - 50) * 2.0;
}

System.out.println("Total: " + total + " euros");
```

### Example 3 (Harder): Multi-Tier Progressive Waterfall

Progressive income taxes and commercial utility billing span 3 or more marginal tiers:

- Tier 1 (0 to 100 kWh): 0.10 euro / kWh (capacity: 10.00 euros)
- Tier 2 (101 to 300 kWh): 0.15 euro / kWh (capacity: 200 kWh $\times$ 0.15 = 30.00 euros)
- Tier 3 (above 300 kWh): 0.25 euro / kWh

For consumption of 350 kWh:
- Tier 1: $100 \times 0.10 = 10.00$ euros
- Tier 2: $200 \times 0.15 = 30.00$ euros
- Tier 3: $(350 - 300) \times 0.25 = 12.50$ euros
- **Total:** $10.00 + 30.00 + 12.50 = 52.50$ euros

```java
int kwh = 350;
double bill = 0.0;

if (kwh <= 100) {
    bill = kwh * 0.10;
} else if (kwh <= 300) {
    bill = 10.0 + (kwh - 100) * 0.15;
} else {
    // 10.0 (Tier 1) + 30.0 (Tier 2) + excess in Tier 3
    bill = 40.0 + (kwh - 300) * 0.25;
}

System.out.println("Electricity bill: " + bill + " euros");
```

The **flat-bracket mistake** occurs when developers charge the entire usage at the highest tier's rate:

```java
// WRONG: Charging all 350 units at 0.25 yields 87.50 euros instead of 52.50 euros
```

```java
    System.out.println("Closed");
```

### Example 2 (Medium): Inverting Separation to Detect Interval Overlap

Two intervals `[start1, end1]` and `[start2, end2]` overlap if they share at least one common point:

```
Interval 1: [  1  ==========  6  ]
Interval 2:             [  4  ==========  9  ]
Overlap:                [ 4 .. 6 ]
```

Instead of listing every overlapping configuration, test when intervals are **disjoint** (share no points):
1. Interval 1 sits completely to the left of Interval 2 (`end1 < start2`), OR
2. Interval 1 sits completely to the right of Interval 2 (`start1 > end2`).

Inverting that condition with De Morgan's Laws yields the overlap test:
- `end1 < start2` flips to `end1 >= start2`
- `start1 > end2` flips to `start1 <= end2`
- `||` swaps to `&&`

```java
boolean overlaps = end1 >= start2 && start1 <= end2;
```

### Example 3 (Harder): Computing Overlap Extent and Boundary Touches

To find the exact duration or length of the shared interval:
- The overlap starts at $\max(start_1, start_2)$.
- The overlap ends at $\min(end_1, end_2)$.
- The overlap length is $\max(0, \text{overlapEnd} - \text{overlapStart})$.

```java
int overlapStart = (start1 > start2) ? start1 : start2;
int overlapEnd = (end1 < end2) ? end1 : end2;

if (overlapStart <= overlapEnd) {
    int length = overlapEnd - overlapStart;
    System.out.println("Overlaps with length: " + length);
} else {
    System.out.println("No overlap");
}
```

### Common Overlap Pitfalls

- **Confusing `<` with `<=`: ** If intervals share a boundary point (e.g. $[1, 5]$ and $[5, 9]$ both contain `5`), `<` considers them disjoint while `<=` recognizes the single-point overlap.
- **Assuming Ordered Intervals:** Never assume `start1 <= start2`. The formula `end1 >= start2 && start1 <= end2` works regardless of which interval starts first.

## 5. The Remainder Operator (%) and Cycles

The `%` operator returns the integer remainder after division, also called the modulo operator.

- `14 / 4` evaluates to `3` (integer division truncates the fraction).
- `14 % 4` evaluates to `2` ($14 = 4 \times 3 + 2$; the remainder is 2).

### Example 1: Parity and Divisibility Checks

Testing whether a number is divisible by 2 (even) or has a remainder (odd):

```java
int number = 7;

if (number % 2 == 0) {
    System.out.println("Even");
} else {
    System.out.println("Odd");
}
```

When checking divisibility by a variable divisor, always protect against division by zero:
```java
if (divisor == 0) {
    System.out.println("Cannot divide by zero");
    return;
}

if (number % divisor == 0) {
    System.out.println(number + " is divisible by " + divisor);
}
```

### Example 2 (Medium): 24-Hour Clock Arithmetic & Midnight Crossing

Cyclic wrapping is called **modular arithmetic**. On a 24-hour clock, adding hours wraps back to 0 at 24:

```java
int currentHour = 22;

int newHour = (currentHour + hoursToAdd) % 24; // evaluates to 3
```

To decompose total minutes into hours and remaining minutes:
1. Integer division (`/ 60`) extracts whole hours.
2. Remainder (`% 60`) extracts remaining minutes.

```java
int totalMinutes = 145;
int hours = totalMinutes / 60;   // 2 hours
int minutes = totalMinutes % 60; // 25 minutes
```

### Example 3 (Harder): Multi-Period Calendars & Gregorian Leap Year Rules

A year is a leap year if it is divisible by 4, except for century years, which must also be divisible by 400.

```java
if ((year % 400 == 0) || (year % 4 == 0 && year % 100 != 0)) {

}
```

### Negative Numbers with the Remainder Operator

In Java, `%` computes the remainder rather than mathematical modulo. If the dividend is negative, the result is negative:

```java
int wrapped = ((val % n) + n) % n;
```
